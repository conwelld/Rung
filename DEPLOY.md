# Deploying Rung

Free tier on Render, roughly fifteen minutes. The app runs under gunicorn with
one worker; Flask's own server is single-threaded and its debug mode ships a
browser console that executes arbitrary Python, so it never faces the internet.

## Before you start

```
python -m tests.test_offline
python -m tests.test_app
```

The offline suite checks the deployment configuration too: that production
refuses to boot without a secret key, that cookies are secure and not readable
from JavaScript, and that `render.yaml` contains no API key.

## 1. Push

```
git add -A
git commit -m "Add deployment configuration"
git push
```

## 2. Create the service

On render.com: **New** → **Blueprint** → pick the repository. Render reads
`render.yaml`, so there is nothing to configure by hand except the key.

## 3. Set the API key

The blueprint marks `ANTHROPIC_API_KEY` as `sync: false`, meaning Render will
prompt for it rather than expecting it in the file. Paste it in the dashboard.
It never touches the repository.

`RUNG_SECRET_KEY` is generated by Render, so there is nothing to do for it.

Use a separate key from your development one, named something like `rung-prod`,
and put a spend cap on the account with auto-reload off. A live URL is
reachable by anyone who finds it, and the app pays for every session.

Optional classroom controls:

- `RUNG_CURRENT_UNIT=2` makes Units 1–2 startable and leaves later material
  visible but locked. The server enforces the same gate as the page.
- `RUNG_INSTRUCTOR_CODE=<long random value>` enables the aggregate instructor
  dashboard. Leave it unset to remove that surface entirely.
- `RUNG_PUBLIC_ORIGIN=https://your-service.onrender.com` enables the absolute
  Open Graph/X preview image tags. It is explicit so forwarded host headers are
  never trusted to construct share metadata.

## 4. Wait for the first deploy

Two to three minutes. `wsgi.py` creates and seeds the database at import, so a
fresh container comes up populated with no manual step.

## What the free tier costs you

**The disk is ephemeral.** `/tmp/rung.db` is wiped on every deploy, restart, and
free-service spin-down, so student data does not survive. Fine for a demo, not
fine for a class. The fix is one environment variable: set `DATABASE_URL` to a
Postgres connection string and `init_db` switches backends through Peewee. The
repository installs the Psycopg 3 driver, but the Postgres path still needs a
live integration run before a class relies on it.

Render's free Postgres is a preview resource: it expires after 30 days and has
no backups. Use paid durable storage—or the institution's database—for a real
semester.

**Cold starts.** The service sleeps after 15 minutes idle and takes 30 to 60
seconds to wake. A recruiter clicking your link may sit through that, so it is
worth hitting the URL yourself before sending it anywhere.

**One worker.** SQLite dislikes concurrent writers, the rate limiter in
`app/server.py` counts per process, and the free tier has little memory. All
three point the same direction. Moving to Postgres is also what unblocks more
workers, at which point the rate limiter needs to move out of process too.

## Running a real class

Three things change:

1. `DATABASE_URL` pointing at Postgres, so data survives deploys.
2. `data/problems.json` with the department's real question bank, which is
   gitignored and would need to be provisioned another way — a secret file on
   Render, or seeded from an admin route.
3. A conversation about `RETAIN_TRANSCRIPTS` and student data before anyone's
   work is stored beyond a session. See SECURITY.md.

4. Campus identity in front of the app. Student handles are a low-friction demo
   identity, not authentication, and the shared instructor code is not a
   substitute for institutional SSO.
